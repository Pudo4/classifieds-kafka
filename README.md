# classifieds-kafka

Сервис объявлений (упрощённый Avito), собранный из нескольких независимых
сервисов, которые обмениваются событиями через Apache Kafka.

Стек: TypeScript (strict, ESM) · NestJS · PostgreSQL + Drizzle ORM (driver:
`pg` / `drizzle-orm/node-postgres`) · Redis · Apache Kafka (KRaft, без
ZooKeeper, клиент `@confluentinc/kafka-javascript`) · Zod · Vitest · Docker
Compose · React + Vite + Tailwind.

## Быстрый старт

```bash
cp .env.example .env
docker compose up -d
```

Одна команда поднимает всё: инфраструктуру (Kafka, Postgres, Redis, MinIO,
Meilisearch), все 7 сервисов и `web`. Каждый сервис, у которого есть своя
база, сам накатывает на неё миграции при старте контейнера (см.
`docker/app/entrypoint.sh`). Дальше открыть **http://localhost:5173** —
это и есть приложение; выбрать пользователя в «Войти как» и пользоваться.

`docker compose ps` — дождаться, пока все сервисы (не только
инфраструктура) станут `healthy`; с нуля это обычно занимает ~30-40 секунд
(первая сборка образов дольше — у `media` и `listing` есть зависимости,
которые надо один раз собрать из исходников). Если какой-то порт на
компьютере уже занят чем-то другим — поменять соответствующий
`*_HOST_PORT` в `.env` (см. комментарии там); на связь сервисов друг с
другом внутри Docker это не влияет, меняется только то, что видно снаружи.

Чтобы разрабатывать один сервис без пересборки образа при каждом
изменении — `cd services/<x> && npm run dev` (запускает его прямо на
компьютере, не в контейнере). Тогда инфраструктуру поднимайте
`docker compose up -d`, а версию этого же сервиса в контейнере — остановите
(`docker compose stop <x>`), чтобы они не спорили за один порт.

## Сервисы

| Сервис | Своя база | Что делает |
|---|---|---|
| `listing` | `listings_db` | Создание/изменение объявлений, их статусы (черновик, на модерации, активно...). Единственный сервис, которому верят насчёт текущего статуса объявления |
| `media` | `media_db` | Приём фото, загрузка в MinIO, создание превью через sharp, удаление данных о местоположении съёмки (EXIF) |
| `engagement` | `engagement_db` | Избранное, просмотры, отклики на объявления |
| `moderation` | `moderation_db` | Проверка объявлений по правилам, история решений |
| `search` | — (Meilisearch) | Поиск. Не хранит объявления сам, а строит поисковый индекс, слушая события от других сервисов |
| `notification` | `notifications_db` | Рассылка уведомлений, их история, живой поток в браузер (SSE) |
| `bff` | — | Единственная точка входа для интерфейса; собирает ответы нескольких сервисов в один |
| `web` | — | Фронтенд на React + Vite: пять экранов, колокольчик с уведомлениями в реальном времени |

Слои внутри каждого backend-сервиса (сверху вниз — от входа к сути):

```
entrypoints/     точка входа: тут HTTP и Kafka подключаются к остальному коду
  ├─ presentation/    контроллеры, проверка входных данных (zod)
  └─ infrastructure/  Drizzle (база), Kafka, обращения к другим сервисам
        ↓
      application/    бизнес-операции (use-cases) + абстрактные интерфейсы к внешнему миру
        ↓
      domain/         сущности и правила их поведения. Не знает вообще ничего
                       про HTTP, Kafka или базу данных
```

Смысл в том, что `domain/` можно читать и понимать, не зная вообще ничего
про NestJS, Drizzle или Kafka — там нет ни одного упоминания этих
технологий.


## Топики

Партиций у каждого топика: 3.

| Топик | Ключ | Что хранит | Кто пишет | Кто читает |
|---|---|---|---|---|
| `listing.events.v1` | `listingId` | Хранит 7 дней | listing | moderation, media, search, notification |
| `listing.snapshot.v1` | `listingId` | **не удаляет старые версии, только последнюю по каждому ключу** | listing | search |
| `media.events.v1` | `mediaId` | Хранит 7 дней | media | listing, search |
| `moderation.decisions.v1` | `listingId` | Хранит 30 дней | moderation | listing, notification |
| `engagement.events.v1` | `listingId` | Хранит 1 день | engagement | search, notification |
| `notification.requests.v1` | `userId` | Хранит 7 дней | несколько сервисов | notification |

`listing.snapshot.v1` устроен по-особенному («compacted» в терминах
Kafka): вместо того чтобы просто копить сообщения и потом стирать по
времени, Kafka хранит только последнее сообщение для каждого `listingId` и
выкидывает более старые. Это позволяет `search`, если понадобится,
восстановить свой индекс с нуля, просто прочитав этот топик заново — там и
так лежит только актуальное состояние каждого объявления.

## Гарантии

**Отправка сообщений.** Явно включены `acks=all` и `enable.idempotence=true`
(`packages/kafka/src/producer.ts`).В проекте всего один
Kafka-брокер, и у каждого сообщения только одна копия. `acks=all` в нынешней конфигурации с одним брокером не имеет преимуществ, необходимо разворачивать 2 и более брокеров.
Ключ каждого сообщения — всегда id той сущности, к которой оно относится (например, id
объявления); без ключа сообщения не отправляются вообще, чтобы гарантировать порядок сообщений об одном и том же объявлении.

**Чтение сообщений.** Автоматическое подтверждение прочитанного выключено
(`enable.auto.commit: false`, `packages/kafka/src/consumer.ts`) — подтверждение
идёт вручную только после того, как сообщение полностью обработано (например,
после записи в свою базу) для защиты от падения процесса.

Поскольку Kafka в принципе может доставить одно и то же сообщение дважды,
нужна защита от повторной обработки. Сделано двумя способами:
- в `search` — по номеру версии: если у входящего события версия меньше
  или равна уже сохранённой, оно просто отбрасывается;
- во всех остальных — таблица `processed_events`, в которую нельзя
  вставить одну и ту же пару (группа потребителей, id события) дважды —
  вторая попытка просто не пройдёт.

**Остановка по сигналу `SIGTERM`.** Метод `consumer.disconnect()` из
`@confluentinc/kafka-javascript` сам дожидается, пока текущее сообщение
дообработается, и только потом отключается от Kafka.

## UI

React + Vite + Tailwind, без серверного рендеринга и без готовой библиотеки компонентов — все элементы интерфейса написаны с нуля. Входа по
паролю нет (см. «Границы» ниже) — в интерфейсе это просто выпадашка «Войти
как» с тремя тестовыми пользователями.

Экраны:

1. **Лента / поиск** — ищет через `search`, запрос идёт через BFF.
2. **Карточка объявления** — BFF собирает её из трёх сервисов: само
   объявление, фото, счётчики просмотров/избранного.
3. **Создать объявление** — форма (можно с фото) → создание → отправка на
   модерацию → переход в «мои», всё одним действием.
4. **Мои объявления** — статусы (`черновик / на модерации / активно /
   отклонено`), причина отклонения, возможность архивировать.
5. **Колокольчик уведомлений** — живой поток из `notification` через SSE
   (Server-Sent Events, односторонний канал от сервера к браузеру); ничего
   не опрашивается по таймеру, уведомление приходит сразу, как только
   появилось.

## Границы

- Нет входа по паролю. Пользователь определяется заголовком `X-User-Id`
  (это просто uuid, проверяется только на корректный формат). Никаких
  JWT-токенов, паролей, регистрации.
- Нет ролей и прав доступа — только проверка «это объявление создал
  именно этот пользователь».
- Поиск — только по тексту, категории и диапазону цены.
- Нет Kubernetes и Helm, нет автоматического деплоя (CI/CD). Только Docker Compose на данный момент.

## Нагрузочное тестирование
  Результат по данным по завершении: 3260 успешно отправленных объявлений → ровно 3260 новых решений модерации → ровно 3260 новых
  записей в `processed_events` у обеих групп потребителей → ровно 3260
  объявлений в итоге стали `active`. Ни одного потерянного, ни одного
  задвоенного сверх уже описанных гарантий — сама доставка сообщений
  работает так, как заявлено.

## Известные ограничения

- **Живые уведомления работают, только пока запущен один экземпляр
  `notification`.** Внутри это просто обёртка над обычным Node
  `EventEmitter` (`InProcessNotificationBus`), которая живёт в памяти
  одного процесса. Если когда-нибудь запустить несколько экземпляров
  `notification` за балансировщиком нагрузки, событие, которое поймал один
  экземпляр, не дойдёт до браузера, подключённого к другому — им
  понадобился бы общий канал связи между процессами, например Redis
  pub/sub. Пока сервис в одном экземпляре, как сейчас, это не проблема.
